# Decisions

Questions that came up while building the module, the answer that was chosen so work could continue, and how to
change it. **"Open" means: please confirm or correct.** Nothing here is hard to reverse yet.

| # | Question | Decision taken | Status / how to change |
|---|---|---|---|
| D1 | What is the module called? | `ServiceDesk` (folder, Gibbon module name, namespace `Gibbon\Module\ServiceDesk`, tables `gibbonServiceDesk*`). No space in the name: URLs and paths need no encoding. Gibbon shows the name as-is in the menu and breadcrumb ("ServiceDesk"). | **Open.** If you prefer "Service Desk" (with a space, like "Help Desk") or another name, say so before the first production install: it is a search-and-replace now, a data migration later. |
| D2 | Extend the Help Desk module or write a new one? | New module, written from scratch. Help Desk was used for ideas only (issues, technician groups, internal notes, assignment, reincarnate). The two modules can be installed side by side; no data is imported from Help Desk. | Decided (as requested). |
| D3 | Who is the "admin"? | Anyone whose Gibbon role has the action **Manage Ticket Types**. They configure the module, see and manage every ticket, and can create shared filters. By default only the Administrator role. | Change in User Admin > Manage Permissions. |
| D4 | How do tickets reach "the suitable team"? | A ticket type lists one or more teams. Every member of those teams sees and processes the tickets of that type. A team can handle many types. No per-team sub-permissions (everyone in the team can do everything on its tickets). | **Open.** Help Desk has fine-grained group permissions (assign / resolve / reassign); say if you need them. |
| D5 | Who can be a team member? | Staff only (people with a staff record). | Change `People::getStaffOptions()`. |
| D6 | Does the other parent of the family see a ticket? | No. A ticket is seen by the person who raised it, the teams of its type, and administrators. | **Open.** A "share with family adults" option is listed under missing use cases. |
| D7 | Which stage changes are allowed? | Team members can move a ticket from any stage to any other stage of its type. Requesters cannot change the stage; they comment. | **Open.** Restricting transitions ("only from New to Approved/Rejected") is possible later. |
| D8 | Where do automation scripts live and who writes them? | PHP classes in `src/Automation/Scripts/`, written by a developer and deployed with the module. Administrators only *choose* a script for a stage. Scripts are not editable in the browser: code typed into a web form and executed on the server would be a serious security hole. | Decided. See `docs/ARCHITECTURE.md` > Automation for the interface. |
| D9 | What happens when an automation fails? | Entering the stage and the script run in one database transaction. On failure everything is rolled back, the ticket stays in the stage it was in, the reason is written on the ticket as an internal note, and the person moving it gets a warning. On success the result is written as a public comment and the ticket moves to the stage's "then move to" stage. | Decided (matches the absence example). |
| D10 | When is an absence recorded in Attendance? | When a team member moves the ticket to **Approved**. The script then marks every chosen child "Absent" for every school day of the period, verifies it, comments, and moves the ticket to **Done**. | To record without approval, put the automation on the first stage ("New") of the Absence Report workflow: it then runs when the ticket is created. |
| D11 | Are unenrolment and de-registration automated? | No: the team does the work in Gibbon (enrolment, finance, account status) and closes the ticket. A ready script *Unenrol from classes* exists and can be attached to a stage; finance and account deactivation are never automated. | **Open.** Tell me which steps you want automated and the exact rule (e.g. which finance records). |
| D12 | What is the default notification policy? | Notification centre **and** email, until the person changes it in *Notification Settings*. Independent of Gibbon's own "receive email notifications" preference. Email needs Gibbon's mail settings to be configured. | **Open.** Change `SubscriberGateway::DEFAULT_POLICY` (e.g. email off for staff). |
| D13 | Who is told about what? | New ticket: all members of the type's teams; **if those teams have no members, the administrators (D3) instead**, so a request never goes unseen. Afterwards: the people who follow the ticket (requester, assignee, anyone who commented or switched notifications on), plus the whole team while nobody is assigned. Internal notes: team only. Never the person who made the change. | Decided. |
| D14 | Who can create shared (default) filters? | Administrators (D3), for an audience (see D31) or for one team. A filter never shows more than the person may see anyway. | Decided. |
| D15 | Can tickets, used ticket types or used stages be deleted? | No. A type with tickets is made inactive instead; a stage with tickets must be emptied first; tickets cannot be deleted at all (they are the record of the request). | **Open** for tickets: a delete/anonymise function may be needed for data-protection requests. |
| D16 | What does a ticket remember of its request form? | A copy of the questions and answers at the time of the request. Later changes to the type's form do not alter old tickets. | Decided. |
| D17 | Is a subject required? | No. If empty it becomes "<type>: <children>". | Decided. |
| D18 | How are ticket type names, field labels and stage names translated? | They are data, typed by the administrator in the school's language. They are passed through the module's translation domain, so a translation file can translate the default ones. | Decided. |
| D19 | How is "create tickets on behalf of others" given? | A second Gibbon action on the request pages, **New Request_onBehalf** (Gibbon's grouped-action convention; this is the name shown in Manage Permissions). Default: Administrator and Support Staff. Holders see every active service (not only those of their own role) and can pick any active user; the form is then built for that person (a parent's own children and classes). The chosen person is the requester; the history line "Created by X on behalf of Y" is public; Y is notified through their own policy. | **Open:** which roles should have it by default (teachers?). Change in User Admin > Manage Permissions. |
| D20 | Can the creator still see a ticket they made for someone else? | Only if they are an administrator or in a team of the ticket's type. Otherwise they return to the service list with a success message. | **Open.** Say if the creator should always follow such tickets. |
| D21 | Which person gets a new ticket when its type has several teams with a default assignee? | The default assignee of the first team by name. The default must be a member of the team; when they leave the team (or are no longer an active user) tickets start unassigned again. The rest of the team is still told about the new ticket. | Decided; simple rule. Round-robin or least-busy assignment is possible later. |
| D22 | How are the comment permissions given? | Two action families in User Admin > Manage Permissions, each with two levels: **Edit Comments_my / _all** (change the text, delete) and **Change Comment Visibility_my / _all** (visible to the requester <-> internal). "_my" = own comments, "_all" = any comment. Default: Administrator both "_all"; Teacher and Support Staff both "_my"; parents and students none. | **Open:** should parents/students be able to edit or delete their own comments by default? Today: grant *Edit Comments_my* to the Parent role if wanted. |
| D23 | What do the comment permissions *not* override? | The ticket rules. The person must be able to see the ticket; internal notes can only be touched by people who work on the ticket; **visibility can only be changed by people who work on the ticket** (administrator or team member), because nobody else can see internal notes. Log lines (stage changes, automation results) can never be edited or deleted. | Decided. |
| D24 | What trace is left? | An edited comment shows "edited" (hover: when). Editing someone else's comment, changing visibility and deleting write a line in the team-only history saying who did it and when - not the old text. A note made visible is announced to the followers like a new comment. Deleting is permanent. | **Open:** say if deleted or previous texts must be kept (audit). |
| D25 | Board: separate "boards" or a view of the ticket list? | A **view** of the Tickets page (List / Board switch). Any filter, personal or shared, can be looked at either way, so a shared filter *is* a team board; there is no extra "Manage Boards" screen. (Agreed with the owner.) | Decided. |
| D26 | Which columns does the board have? | The filter decides. Exactly one ticket type in the filter: that type's workflow stages, and cards can be dragged between them. Anything else: Open / In Progress / Closed, as an overview without drag and drop (a status is a different stage in each workflow, so a drop would be ambiguous). | Decided. |
| D27 | Who gets the board, and what is remembered? | Team members and administrators. Requesters keep the list. The page remembers **per person** whether they last used the list or the board (one choice for the whole page, not per filter) and opens that way next time, also after logging in again. | **Open:** say if the choice should be remembered per filter instead. |
| D28 | What happens when a card is dropped? | The same as changing the stage on the ticket page (same permission checks, history, notifications, automation). A stage with automation asks for confirmation first; if the automation fails the card is back in its column after the reload and a warning is shown. The page reloads after each move (simple and safe; no background requests). | Decided. |
| D29 | How long do closed tickets stay on the board, and how many cards? | Closed tickets for 30 days after closing; at most 300 cards (a note asks to narrow the filter beyond that). Both are constants at the top of the board section in `tickets.php`. The list is not affected. | **Open** if other numbers suit you better. |
| D30 | Colours | Status colours (amber / blue / green) on stage tags and column tops; one colour per ticket type, chosen by the administrator, as the stripe of a card and a dot in the list; High and Urgent priority as a marker on the card. | Decided. |
| D31 | Who sees which shared filters? | Every shared filter has an **audience**, chosen by the administrator when saving it: *Staff working on tickets* (administrators and team members; optionally one team) or *Requesters*. A person is an agent only if they are an administrator or a member of a team that has ticket types; **everybody else is a requester** - parents, students, and staff who are in no team - and sees what requesters see. (Agreed with the owner.) Defaults: agents get My Requests, Open Tickets, Assigned to Me, Unassigned (+ Absence Intake for team Administration); requesters get Open and Closed, next to All. | Decided. |
| D32 | What does the administrator see? | Every shared filter, including those for requesters (shown dashed, marked "(requesters)") and for other teams, so they can check and delete them. | Decided. |
| D33 | How does deleting a saved filter ask for confirmation? | The "Delete filter" link opens a confirmation page (Gibbon's standard delete form); a shared filter says it will disappear for everyone. | Decided. |
| D34 | Who counts as "both parents of a family"? | The other adults in a family (Gibbon's family record) of the requester, **with data access = Yes**, active users. Shared per **ticket type**: the type setting *Share With Family* (default Yes for Absence Report, Course Unenrolment, School De-registration; No for Complaint and General Request, because a complaint may concern the other parent). They see the tickets in the list, comment, withdraw and reopen, and are told about public updates with their own notification settings (a row for the ticket overrides it). They do not get the board, nor internal notes. | **Open:** is Complaint / General Request right as "private"? Change per type in Manage Ticket Types. |
| D35 | What does "withdraw" do, and when? | The requester (or the other adult) moves the ticket to the workflow's **Withdrawn** stage (a stage flagged *Withdrawn Stage*; every default workflow has one; one per workflow, status Closed). Allowed while the ticket is Open or In Progress. A written note is optional; the team is told. A workflow without such a stage offers no withdraw. Attendance or enrolment already changed by an automation is **not** undone. | Decided by the owner: a switch per ticket type, see D45. |
| D36 | When can a closed request be reopened? | By the requester side for **30 days** after it was closed (constant `TicketAccess::REOPEN_DAYS`), whether it was Done, Rejected or Withdrawn. It goes back to the first stage of its workflow (its automation, if any, runs again). After 30 days a new request is needed. | Whether requesters may reopen at all is a switch per ticket type (D45). **Open:** other number of days? |
| D37 | Who is "the teachers" to tell, and what do they read? | The automation script *Tell the teachers* on a stage (since 1.6.00, see D44; default: the *Approved* stages of Absence Report and Course Unenrolment). Recipients: the **form tutors** of the children and, for an absence, every **teacher of the children's classes** this year; for an unenrolment only the **teachers of the chosen classes**. Notification centre only - **never email**, whatever the teacher's settings. The text names the children, the classes (unenrolment) and the dates, **not the reason** (it stays on the ticket). The person who approved is not told. Teachers cannot open the ticket (they are not in the team); the notice links to their notification list. | **Open:** should assistants also be told? |
| D38 | Which unenrolment stage tells the teachers? | The Course Unenrolment workflow gets an *Approved* stage whose only automation is *Tell the teachers* (the team still updates enrolment and finance by hand, D11). The team moves the ticket there when they have agreed, then to Done. The script can be ticked on any stage of any workflow. | Decided. |
| D39 | Dashboard widgets (replaced in 1.7.00 by the sidebar box, see D46) | A tab "Service Desk" on the **parents'** dashboard (my open requests, including the family's shared ones; link to send a new one) and on the **staff** dashboard: team members and administrators see *Unassigned tickets* and *Assigned to me* (5 newest each, with totals, links to the board and the list); other staff see their own open requests. Students get no widget. | **Open:** add one for students? |
| D40 | Moving a ticket to another ticket type | Team members and administrators, with the "Move to Another Ticket Type" form on the ticket (any other **active** type). The ticket keeps the stage of the same name or starts in the first stage of the new workflow (no automation runs); the assignee stays only if they are in a team of the new type; the answers are kept as they are (scripts of the new type may then find fields missing and fail safely). The requester sees the move. The person may lose sight of the ticket if they are not in the new type's team. | Decided. |
| D41 | Deleting tickets (data protection) | New action **Delete Tickets** (default: Administrator). Holders can delete tickets **they can see**, from the ticket page, after a confirmation page. Removes the ticket, its comments, notification settings and the notifications about it; keeps changes the workflow made elsewhere (attendance rows carry the comment "Service Desk #n"); writes a line in Gibbon's log (that, when and by whom - no content). Permanent. | **Open:** a DPO who may delete but is not an administrator cannot find tickets: give them team membership or the administrator role. |
| D42 | Retention per ticket type | Field *Retention (days)* on the ticket type; empty = keep for ever. The script `cli_deleteExpiredTickets.php` (cron, e.g. nightly; `--dry-run` to try) deletes **closed** tickets that were closed longer ago than that, the same way (and logs "after its retention time"). Open tickets are never deleted. Nothing runs by itself: the school must schedule the script. | **Open:** defaults per type (none set). |
| D43 | What does the search cover? | Words (all must be found) in: ticket number, subject, the answers of the request form (details, children, classes, dates, list values), requester name, assignee name and **public** comments. Internal notes are never searched. Tickets made before 1.5.00 are searched through their stored answers (which also contain field names). It works in the list, the board and saved filters, always inside what the person may see. | Decided. |
| D44 | Teacher notices as an automation option (asked by the owner) | "Tell the teachers" is an automation script like the others, and a stage can now run **several scripts** (a tick list on the stage form). They run in the listed order inside one transaction: if one fails, none takes effect - so no teacher is told about an absence that could not be recorded. A script's result line can be internal (team only); the teacher line is. The upgrade converts stages that used the old switch. | Decided. |
| D45 | Withdraw and reopen as ticket type options (asked by the owner) | Two switches on the ticket type: *Requesters Can Withdraw* and *Requesters Can Reopen*, both on by default. Off: the link disappears and the page refuses; the team can still move the ticket. Example: switch withdrawing off for Absence Report if an approved absence must not be withdrawn by the parent. | Decided. Defaults are "on" for every type - tell me if a default type should start "off". |
| D46 | Where are a person's open tickets shown on the home page? (asked by the owner) | In a **box in the sidebar, below the Message Wall**: "My open requests" for requesters (own, and the family's shared ones), "Open tickets for me" for team members and administrators (assigned to them or to nobody). It lists the **two** most recently updated (updated ones first), with the total and links. **No box when there is no open ticket.** For parents, students and staff. It replaces the dashboard tabs. | Decided. The number (2) is `DashboardWidget::LIMIT`. |
| D47 | How does the box get there without changing Gibbon? | **No core or index file is changed; everything is in the module folder.** Gibbon runs a module on the home page only through a dashboard tab hook (for parents once per child). The hook puts the box into Gibbon's own "sidebar extra" slot at the bottom of the sidebar, and returns a tab whose script removes that tab again. If a future Gibbon changes its tab markup, the worst case is a small "Service Desk" tab with a link - nothing breaks. A parent with no children on the dashboard gets no box (Gibbon builds no dashboard for them). | Decided; tested on v31. Re-check after a Gibbon upgrade (`tests/live/widgets.js`). |
| D48 | How is "there is an update" shown? (asked by the owner) | Tickets that changed **since you last opened them** carry a red "Updated" mark and are bold - in the list, on the board and in the sidebar box. Opening the ticket clears it for you. Your own changes never mark a ticket for you. Requesters are only alerted by changes they can read (an internal note does not mark it for the parent). A ticket you never opened is marked while it is not closed (so a new ticket is "Updated" for the team). After the upgrade, requesters and assignees start with their existing tickets unmarked. | **Open:** say if only comments (not stage changes or assignments) should mark a ticket. |
| D49 | Sorting in the list | The list starts with updated tickets first, then the most recent "Last Update" (now shown as "2 hours ago" plus date and time). Clicking a column heading sorts by it (number, subject, requester, stage, assignee, priority, last update); a second click reverses. | Decided. |
